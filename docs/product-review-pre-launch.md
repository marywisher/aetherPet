## 0. 增量整体评价

**方向成立，叙事修正（§7.1.2「不喂给第三方 AI」→ 数据主权主线）是对的，且与 CONTEXT.md「数据主权」术语完全对齐，避免了把聊天数据与 AI 能力对立的伪命题。** 增量五件事里，「克制级引导」红线（无教程 UI / 无打卡字样 / 文案全归素材包）保持了产品纪律一致性；「小刺猬」定像理由（自然系小物、避开猫狗赛道、不与青蛙 IP 撞车）站得住。但增量在两个地方与既有事实打架：其一，`first_meeting`「初见=首页第一条」的断言会被**首开同步时自动发放的 daily_grant 事件**（ts 晚于创建时刻）顶下去，A1 验收在真实首开路径下不成立；其二，素材包契约从「包级回退」悄悄扩到「字段级回退」，而现有 loader 架构与 A5 验收都没有完整覆盖。另有倒推事件文案池里混着「梦见你了」类预设认知文案、handoff 与需求文档叙事残留冲突两处小雷。总体判断：**1 个 P0 + 4 个 P1 修掉即可进入开发，不需要回退。**

## 1. P0 · 阻塞项

### P0-1 · 首开路径上 `daily_grant` 事件会把 `first_meeting` 顶下首页第一条，A1 验收在真实场景不成立

**问题描述**
§7.1.3① 定义 `first_meeting` 的 `ts = 创建时刻`，靠「时间线倒序」让它自动成为首页第一条；A1 验收也断言「新账号创建 pet 后首开首页，时间线第一条为 `first_meeting`」。但新账号首开首页必然同时触发 sync，而 sync 会对新 pet 自动发放当日馈赠并**插入一条 `daily_grant` 事件**，其 `ts` 晚于创建时刻（同一分钟级窗口内），倒序排列后首页第一条变成「信箱里多了一个小礼物」，初见字条被挤到第二条。「初见=最新」的叙事结构在最关键的初见场景被自家机制破坏。

**证据**
- `src/app/api/sync/route.ts`：sync 主流程调用 `grantDailyItem`（「每日馈赠检查」段落，`dailyGrant: { ran, granted, skipped }` 直接回传给首页）；
- `src/domain/gift/daily-grant.ts` 头部注释：「首次登录领取物品；事务内写 inventory + **event** + pets.daily_grant_last_date」——馈赠不只是 UI 卡片，是一条入库事件；
- `src/app/page.tsx` L214：「今日馈赠欢迎卡片（sync 自动发放，仅当日首次显示）」——首开当日卡片必然在场；
- 新 pet `dailyGrantLastDate: null`（`src/app/api/pet/create/route.ts` insertPet），首开 sync 必然命中发放条件。

**后果**
- A1 验收用例（新账号 → 创建 → 首开首页）实际看到的是馈赠卡，初见字条排第二；按验收字面执行会「验收失败」，团队被迫二选一：改 A1 文案 或 改发放时序——两者都是返工；
- 初见叙事（§7.1.3①「字条自动成为首页时间线第一条」）在产品层面落空：新用户的第一眼是「信箱多了一个小礼物」而不是「小刺猬摊着一张字条」，初见仪式感被馈赠机制稀释；
- 收尾句承诺「下次回来的时候……会给你带礼物」（§7.1.3③）与「第一天就发礼物」在语义上也不完全对齐——第一天已经发过了。

**建议修复**（三选一，推荐 a）
- a. **首发馈赠顺延至次日**：新 pet 的当日首登不发馈赠（`grantDailyItem` 对「创建当日」跳过），馈赠落在 T+1 首次登录。副作用最小：MVP §3.7「当天首次登录奖励」的本意是「打开就有仪式感」，而新用户当天已经有了更强的初见仪式（字条 + 倒推小日子 + 收尾句），T+1 发礼物反而让收尾句「下次回来给你带礼物」的预告精确兑现，叙事闭环更干净。需在 §7.1 加一条决策：「创建当日不触发每日馈赠，首日馈赠自次日开始」，并回归验收 10；
- b. 保留当日馈赠，首页时间线对**未读过的 `first_meeting` 做一次性置顶**（渲染层 pin，非 ts 排序破坏），A1 文案改为「首开时初见字条置顶展示」；
- c. 接受现状，把 A1 改为「首开 24h 内初见字条出现在时间线前两条」——不推荐，初见叙事会被弱化。

无论选哪个，A1 与 §7.1.3① 的「自动成为第一条」表述必须同步改写，避免验收歧义。

## 2. P1 · 高价值问题

### P1-1 · handoff 与需求文档的叙事残留冲突：旧版「不喂给第三方」仍写在执行清单里

**问题描述**
§7.1.2 已把差异化叙事修正为「数据主权 / 资产归个人 / 可迁移 / 停运可换中心续玩」，并明示「不对外宣称『不喂给第三方』」。但增量来源文档 `session-handoff-pre-launch.md` 的背景结论与执行清单第 7 条仍写着旧叙事（「开源 + 自托管 + 不把你的聊天喂给第三方 AI 服务」「发布三件套……『为什么 AI 陪伴游戏把你的聊天喂给第三方服务，而这个不会』说明段落」）。handoff 是下一会话的执行指令，开发者照单出 README 文案时大概率写出旧口径，与 §7.1.2 冻结决策直接冲突。

**证据**
- `docs/session-handoff-pre-launch.md` 头部背景结论 + §二第 7 条（原文引用，见上）；
- `docs/requirements.md` §7.1.2：「明示：AI 对话等能力按需作为插件接入（未来），不对外宣称『不喂给第三方』——不把聊天数据与 AI 能力对立」。

**后果**
- README / why-self-hosted 出稿时两套叙事并存，发布物料自相矛盾；「不喂给第三方」这类绝对化表述一旦被插件生态（未来 AI 对话插件）打破，就是公开自证谎言；
- 旧叙事还带「抢在 Froggy Roams 上线前发布」的竞对锚定，与 §7.1.2「不对标 Froggy Roams」也冲突。

**建议修复**
- 在 `session-handoff-pre-launch.md` 顶部加一条「⚠️ 叙事修正」注记（或删改 §一背景 + §二第 7 条），明确 §7.1.2 为准；
- 发布三件套的文案模板直接以 §7.1.2 主线为唯一输入：「你的 pet 与其记忆属于你，不属于任何一家厂商；即使官方停止运营，导出数据换个服务中心，它依然活着」。

### P1-2 · 倒推初始事件的文案池混入「预设认识你」的变体，与「它在你遇见它之前就住在这里」叙事自相矛盾

**问题描述**
§7.1.4 把初始事件限定在家类型池（`watching_water / counting_leaves / self_talk / spontaneous_letter`），`ts` 倒推至创建前 6~48h，叙事是「它在你遇见它之前就住在这里」。但倒推事件发生在**初见之前**——那一刻 pet 还不认识用户，而默认包 `spontaneous_letter` 文案池里包含直接面向「你」的变体。倒推事件一旦抽中这些变体，新用户翻时间线看到初见之前的日子写着「昨晚梦见你了」「飘到你那儿」，叙事穿帮：它还没认识你，怎么梦见你？

**证据**
- `src/assets/packs/default/text/spontaneous-letter.json` L7：「昨晚梦见你了，醒来还有点想」；L18：「我把 {recall_line} 折成纸船，让它顺着风飘到你那儿」；
- `src/app/api/pet/create/route.ts`：初始事件经 `generateBatchEvents(pet, [], initialCount)` 随机抽池，现有逻辑无任何「排除 user 指向变体」的过滤；
- `self_talk` 的 `{recall_line}` 兜底为「没什么特别的」（`src/domain/events/render.ts` L120）——兜底安全，不用改；风险集中在 `spontaneous_letter`。

**后果**
- 初见叙事的「过去小日子」时段被 2 条预设认知文案污染，与 §7.1.4 的叙事意图直接矛盾；
- 概率不高（自发冒信池的 11 条中约 2 条面向「你」，且只影响新 pet 首屏翻查），但一旦出现就是低成本的「穿帮感」。

**建议修复**
- 引擎「类型池覆盖」选项（§7.1.4 本来就要新增）上加一层过滤：初始事件仅抽取**不含 user 指向**的变体。落地形态二选一：① 素材包 text 文件给变体加可选标记（如 `"addressed_to_user": true`），初始事件池跳过标记变体；② 更轻量：初始事件池直接缩为 `watching_water / counting_leaves / self_talk`（`self_talk` 无「你」指向，已核实），`spontaneous_letter` 整体挪出初始池。推荐 ②，契约零改动。
- A2 验收补一句断言：「倒推事件不含面向『你』的文案变体」。

### P1-3 · 素材包「字段级回退」是新增语义，现有 loader 只有「包级回退」，A5 验收未覆盖资产键与第三方包的向后兼容

**问题描述**
§7.1.5 规定 `manifest.texts.first_meeting / guidance` 可选，「缺则该包渲染时回退 default 包同名文案」。但当前架构的回退是**包级**的：pack 健康检查不通过 → 整包换成 default（`fallback.ts`：`effectivePack = defaultPack, fallbackReason = health.reason`），不存在「主题 CSS 用 A 包、`first_meeting` 文案用 B 包」的字段级混合回退。另外 `first_meeting_note` 资产键的回退语义完全没写：包缺文案时插图从哪来？包缺资产键时呢？

**证据**
- `src/domain/packs/fallback.ts`：回退粒度为整包（`return { effectivePack: defaultPack, fallbackReason: ... }`）；
- `src/domain/packs/manifest-schema.ts`：`texts` 对象 11 键全必填 + `catchall(z.string())`——`first_meeting` 键今天就能被 catchall 吃掉，但**没有**被 loader 健康检查消费，也没有「缺键回退默认文案」的渲染路径；
- 现网已有 3 个包（`src/assets/packs/default | morning | night`），升契约 1.1.0 后它们都**没有** `first_meeting` / `guidance` 键。

**后果**
- 1.1.0 引擎 + 1.0.0 旧包（morning/night）渲染 `first_meeting` 事件时：若按「整包健康=通过、字段缺→回退 default 同名」实现，用户会看到「morning 主题 + default 文案/插图」的混合体——不崩溃但观感错位；A5 只断言「不崩溃 + 回退同名文案」，没断言混合观感是否可接受、资产键缺失时展示什么；
- 第三方包作者视角：可选键 + 回退默认 = 老包零改动继续可用（好），但契约文档（`packs-contract.md` §2 约束表、§6 渲染规则）不写明「字段级回退优先级（自身键 > default 包同名键 > 无图占位）」，作者不知道混合渲染行为，出了观感 bug 会往引擎上赖；
- 渲染兜底缺项：未知/缺失资产键当前无定义行为（`assets` 是 `z.record` 自由键，前端取 `first_meeting_note` 取不到时行为未定）。

**建议修复**
- `docs/packs-contract.md` 增补字段级回退规则并升契约版本说明：`texts.first_meeting` / `texts.guidance` / `assets.first_meeting_note` 三者均为「缺失 → 回退 default 包同名键；default 也缺 → 降级为无插图纯文案卡片」，并把该规则写进 A5；
- A5 验收扩为三条用例：① 无新键的旧包（morning/night 现成）渲染 `first_meeting` 事件不崩溃、文案/插图来自 default；② 自造包只写 `first_meeting` 不写 `guidance`，文案来自 default 而桌面小字可用；③ `first_meeting_note` 资产键缺失时展示降级形态（无插图卡片）；
- 官方包 `default`、`morning`、`night` 建议本期顺手补上新键（成本极低），消除官方包的混合观感；
- `guidance` 文件的结构要定死（`desk_hint` + `first_session_farewell` 两键，`{pet_name}` 占位符替换发生在前端渲染时），写入契约 §3 或新小节，避免各写各的。

### P1-4 · 导出/导入链路对 `first_meeting` 与「倒推事件早于 pet 创建时刻」缺少前向兼容规则，数据主权故事的关键一环有暗坑

**问题描述**
§7.1.2 的核心承诺是「导出数据换个服务中心，它依然活着」——这要求导入链路对新事件类型与倒推时间戳**宽容**。两个暗坑：① 新增 `first_meeting` 事件会随导出 JSON 进入事件时间线（type 为字符串值）；旧版（1.0.0 引擎）中心的导入器/时间线拿到未知类型后行为未定义（UI 层 `TYPE_LABELS` 未命中时显示原始英文 type 字串，渲染层按 type 查包文案查不到 → 崩溃或空卡）；② 倒推初始事件 `ts` 早于 `pet.base.created_at`（§7.1.4 倒推 6~48h），若任何校验（导入器、QA 比对、未来审计）断言「事件 ts ≥ pet 创建时刻」，会被自家数据打脸。

**证据**
- `src/domain/export/schema.ts`：导出事件 `type: string`（宽容）；`src/domain/export/importer.ts` 按原样重建事件（`createdAt: e.created_at ?? e.ts`），importer **不**走 pet create 路由——所以「导入会重新触发 `first_meeting`」目前不成立，这是好消息；
- `src/ui/event-card.tsx` L79：`TYPE_LABELS[event.type] ?? event.type`——未知类型裸显示英文 type 字串（对中文用户是观感事故，非崩溃）；
- `src/assets/packs/default/text/` 11 个文件——1.0.0 包没有 `first_meeting` 文案文件。

**后果**
- 发布后 12 月前若用户把含 `first_meeting` 的导出拿到旧版本自托管实例导入：初见字条在旧实例上显示为裸 type 字串或空白卡，正好打在数据主权故事最核心的「迁移续玩」场景上；
- 倒推时间戳若被导入校验或 QA 脚本当异常处理，会误报「数据损坏」。

**建议修复**
- 定一条兼容规则并写进 §3.9 与契约：「未知事件类型的渲染降级 = 通用卡片（type 中文化映射表 + default 包兜底文案），不崩溃」；`TYPE_LABELS` 未命中时按此降级实现；
- 在导出规范 v1 的元信息里注明事件 type 可能出现「导出端已知、导入端未知」的新值，导入器对未知 type 采取「保留入库 + 渲染降级」而非拒绝；
- 在 §7.1.4 或 `CONTEXT.md` 补一句领域语义：「pet 的倒推初始事件 ts 可以早于 pet.created_at，这是『初见前它已在此』叙事的一部分，非数据异常」，防 QA/审计误判；
- 加一条回归测试锁死「导入路径永不重新生成 `first_meeting`/初始事件」（今天是对的，但要防未来重构把生成逻辑挪进 sync）。

## 3. P2 · 中低优先级问题

### P2-1 · 引导文案 ②「桌面小字」与首页馈赠卡的互斥关系在首日失效，建议把语义写明白而非改逻辑

**问题描述**
§7.1.3② 定义小字「可以把东西放桌上给我」= placeholder 语义（馈赠卡缺席时显示、有内容隐藏）。但首开当日 sync 自动发馈赠 → 馈赠卡**必在场** → 小字首日被隐藏；小字真正出现的窗口是「卡片缺席日 + 物品栏空态」。逻辑自洽（卡片在场时卡片文案「放桌上，看看它会怎么回应吧」已承担提示职能，小字隐藏不丢信息），A3 验收字面也成立。问题只在文档没写清这个互斥关系，开发/QA 容易按「小字常驻」实现，A3 的「有内容（有卡/有物品）隐藏」措辞也给了误读空间。

**建议修复**
- §7.1.3② 补一句：「馈赠卡在场时，提示职能由卡片文案承担，小字隐藏是预期行为（含首日）」；A3 保持不动。

### P2-2 · `first_meeting` 生成与 pet 创建的事务边界未定义

**问题描述**
§7.1.3①「创建 pet 时仅触发 1 次」。`create` 路由现有实现：先 `insertPet` → 写命名记忆 → `generateBatchEvents` + `insertMany`（非事务可见）→ 审计日志。若 `insertMany` 失败而 `insertPet` 已落库：重试 create 返回 409（「该账号已拥有 pet」），`first_meeting` 与初始事件**永久缺失且无补偿路径**——一个真实用户会看到空时间线，且没有任何机制补发。

**建议修复**
- 把 `insertPet + 命名记忆 + first_meeting + 初始事件 + 审计` 收进单事务（仓库层已有 `withTransaction` 基建）；
- 或加一条自愈规则：sync 时发现 pet 无 `first_meeting` 且无初始事件 → 按当前时刻补齐（不推荐，叙事上「初见」迟到了几天——但优于永久缺失，可作为 P3 兜底）。

### P2-3 · `packs-contract.md` 同步清单的「source」维度缺 `creation`，§8.4 清单本身需要微修

**问题描述**
§7.1.5 的同步清单（八项 + `TYPE_LABELS` + manifest-schema + 契约单测 11→12+2）基本齐全，但 `packs-contract.md §5` 事件契约表的 `source` 列只有 `engine / gift / catchup / system` 四种取值，`first_meeting` 的触发源是「创建时刻一次性」，需要新增 `creation` 值；同时 §8.5「已知限制」与 `RANDOM_TYPES` 注释（「引擎可随机触发的类型」）要在文档里明确「`first_meeting` 不进 `RANDOM_TYPES`、不进补算」——这两条 §7.1.3① 写了，但契约文档没有落点，实现者容易在 `generateBatchEvents` 默认池里顺手加进去。

**建议修复**
- 契约 §5 表加一行：`first_meeting | creation | —（无 params） | — | 0 | no-op`；§8.4 清单补「`RANDOM_TYPES` 显式排除」为验收条件；单测断言 `RANDOM_TYPES` 与补算池均不含 `first_meeting`。

### P2-4 · 首会话收尾句 localStorage 方案的边界已自知，建议补一句「多 pet 未来」的语义

**问题描述**
§7.1.3③「双落点只亮一次 + localStorage 按 petId 标记」+ §7.2「换浏览器重复一次可接受」——边界自知，方案成本低，**可接受，不建议换服务端方案**（服务端标记与「本期不做服务端标记」已决，且换设备重复一次收尾句不构成体验事故）。唯一的语义空档：MVP 每账号 1 pet，按 petId 标记没有差别；未来多 pet 时「每个新 pet 各亮一次收尾句」是合期望还是 bug？文档没写。

**建议修复**
- §7.2 加一句：「按 petId 标记即『每只 pet 的首会话各亮一次』，多 pet 时期望行为不变」，防止未来迭代争论。

### P2-5 · 发布三件套文案的两处措辞风险

**问题描述**
① 「旅行青蛙停服后，你的蛙就没了。AetherPet 不会。」——前句是**对第三方产品数据命运的事实断言**（「就没了」未经证实，且停服时间本身是预测），后句「AetherPet 不会」是绝对承诺，但 AetherPet「不会」依赖用户真的执行了导出/自托管/换中心——官方托管中心的用户若不做任何备份，官方停服时他们的 pet 一样没了，这个承诺会被反噬。② 「资产归个人」——注意 pet 的**数据**（记忆/时间线/物品）归用户，小刺猬形象与素材图是项目版权资产（开源协议下属于社区），why-self-hosted 里把「资产」与「数据」混用会留下「厂商素材归我所有」的误读空间。

**建议修复**
- 前句软化为可证伪性更低的对比叙事：「旅行青蛙停服之后，它的记忆没有地方可去。AetherPet 的数据从一开始就在你手里——停服、迁移、自托管，它都跟着你走。」把「就没了」的断言权交还给用户判断；
- 后句绑定机制：「AetherPet 的数据可随时导出、可自托管、可换中心续玩；即使官方哪天停止运营，它依然活着」——用「即使官方停止运营」替代「不会」，承诺落在机制而非品牌；
- why-self-hosted 用词统一为「你的记忆与时间线属于你」，素材另说「形象与素材以开源协议共享」。

### P2-6 · 小刺猬资产接线：首页/信纸/时间线三处落点建议分级，避免时间线视觉过载

**问题描述**
§7.1.1 + handoff §二第 5 条要把小刺猬 3 状态图「接线进首页/信纸/时间线」（死资产变活）。首页用状态图是核心落点（初见场景「小刺猬已坐在桌上」直接依赖它）。但时间线是**高频长列表**（补算后一次可能十几张卡），每张卡都挂 pet 状态图会抢走事件文案与记忆高亮的视觉焦点，与「低频、克制」调性冲突；信纸场景（回信/冒信）配一只刺猬头像则合适且成本最低。

**建议修复**
- 分级接线：首页 = 全尺寸状态图（3 状态切换）；信纸类事件卡（`reply_letter / spontaneous_letter / first_meeting`）= 小头像/角标；时间线普通卡 = 不挂图，保持现状纯文案卡。§7.4 的「前端接线」范围按此收窄，避免全量时间线改卡。

## 4. P3 · 建议（不阻塞）

1. **跨版本兼容测试夹具**：CI 里加一条「1.0.0 引擎 + 含 `first_meeting` 的导出 JSON」的渲染降级用例（对应 P1-4），防止发布后自托管旧实例变成数据主权故事的反面教材。
2. **倒推时间窗口 6~48h 的取值**：48h 上限意味着新用户翻时间线最多看到 2 天前的「小日子」，与「过去 X 天」聚合入口卡的分组（`src/ui/timeline.tsx` `TimelineEntryCard`）无死角——倒推事件会被卷进后续任何跨天补算的聚合区间里正常展示，这块不用改；建议 QA 用例里加「创建后离线 8 天回归 → 倒推事件与每日聚合同屏」一条即可。
3. **README 时效性**：借势钩子绑定「12 月旅行青蛙停服」这一时间窗，停服发生前后 README 钩子文案要有一版「已停服」措辞切换，建议现在就把两套文案（预期态/既成态）都写进 README，省一次发布后的文案返工。
4. **竞对定位存档**：handoff 的止损线（star < 200 且自托管实例 < 50 → 维护态）与「不对标 Froggy Roams」已定，建议在 `docs/` 里把 Froggy Roams 的定位差异（Steam 单机买断 + AI 明信片 vs 本项目的 Web 开源 + 数据主权）固化成一段，避免后续会话重复调研。

## 5. 遗漏场景补充（不在 §7 里但增量必须考虑）

- **创建接口部分失败**（pet 落库、事件未落库）：见 P2-2，无重试通道（409 挡住）。
- **导入到新中心后再次注册/创建**：导入路径不走 create 路由，不会重复生成 `first_meeting`（P1-4 已给回归测试建议锁死）。
- **老版本自托管实例导入新导出**：未知事件类型渲染降级（P1-4 / P3-1）。
- **换设备/清缓存后首会话收尾句重复一次**：已自知接受（§7.2），补语义见 P2-4。
- **官方包 morning/night 未补新键**：1.1.0 引擎下渲染 `first_meeting` 会出混合观感（P1-3 建议本期顺手补齐三个官方包）。
- **README 停服时点跨越**：预期态/既成态两套文案（P3-3）。

## 7. 结论

**建议：通过（附修订条件），不回退。**

增量的产品方向（克制引导、初见叙事、数据主权主线、小刺猬定像）均成立，红线（无教程 UI / 无打卡字样 / 文案归素材包）与既有纪律自洽。修订项清单（进入开发前必须处理）：

| 级别 | 项 | 处置 |
|------|-----|------|
| P0 | P0-1 首开馈赠卡顶掉初见字条（A1 验收字面不成立） | 必须三选一定案并改写 §7.1.3① / A1 |
