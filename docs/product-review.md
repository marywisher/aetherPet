# aetherPet MVP 需求文档 · 产品专家评审报告

> 评审日期：2026-09-09
> 评审范围：`docs/requirements.md`（MVP 需求，11 项验收）与 `CONTEXT.md`（领域术语表）
> 评审视角：AI 陪伴产品 / 开源生态 / 虚拟宠物养成品类的行业最佳实践

---

## 0. 总体判断

**结论：整体方向 OK，理念自洽度高，但需要 4 个 P0 级修补后进入开发；不建议整体回退。**

需求文档的三大支柱——**佛系纪律、数据主权、表现与逻辑解耦**——在术语表里定义得清晰，MVP 11 项验收也抓住了核心体验（pet 状态机、随机事件引擎、补算、每日馈赠、回信）。旅行青蛙式的「低频 + 有记忆 + 无社交」定位是稀缺的、可做的，方向不摇摆。

但以下 4 个 P0 问题如果不修补，会让 MVP 一上线就与自家理念自相矛盾：

1. **补算的极端场景未封顶**——3 个月离线会一次性生成上百事件，直接击穿「低频」理念，也违反性能指标。
2. **数据导出/导入的 schema 完全没定义**——「数据主权」是核心承诺，验收却只写「一键导出 JSON」，未来多中心迁移一定爆雷。
3. **无密码账号的安全与恢复闭环未定义**——验证码一次性还是每次都用、会话时长、被盗找回、被盗后数据完整性验证——这些边界缺失，「数据主权」反而会变成反噬（账号被劫持 = pet 历史被劫持）。
4. **「记忆引用」作为灵魂体验，验收未覆盖**——CONTEXT.md 反复强调「活人感 + 有记忆」，但 11 项验收里没有任何一项验证 pet 能否正确引用历史记忆。

P0 修补后，MVP 可以进入开发。P1/P2 是打磨与后续迭代，不阻塞。

## 1. P0 · 高优先级问题（阻塞开发启动）

### P0-1 · 补算机制缺「长时间离线」的封顶与渐进披露 → 会与「低频」理念直接冲突

**问题描述**
CONTEXT.md 定义补算为「一次性补算错过的随机事件」，验收 4 只测「离线 3 天」。但真实用户行为中：
- 长期出差 / 搬家 / 换设备 / 半年忘了登录都很常见；
- 假设事件引擎日均产出 ~3 个事件，3 天 ≈ 9 个，1 个月 ≈ 90 个，3 个月 ≈ 270 个；
- 一次性生成 270 个事件 → 时间线被冲垮 → 「打开 APP 就是信息轰炸」→ 直接违反「低频交互、少打扰」的产品原则。

此外，补算期间 pet 状态机如何连续推进（离线前在家 → 离线期间是否出门旅行 → 回来时状态），文档也未定义。

**影响**
- 与「佛系、低频」定位直接冲突，第一次长期缺席的回归用户会立刻对理念失去信任；
- 违反性能指标「补算在秒级内完成」（270 个事件 + 记忆检索 + 状态推进，秒级不可能）；
- 时间线 UX 崩溃（首屏渲染、分页压力）。

**建议处理方式**
1. **给补算设硬上限**：单次补算生成事件数 ≤ N（建议 N=20）；超出部分**只生成一条聚合摘要事件**（例：「过去 30 天，Pet 出门走了 4 次、收过 2 片枯叶」），细节留到用户主动点击展开；
2. **时间分片**：超过 7 天的离线按「每天 1 条聚合」生成，避免堆积；
3. **补算结果渐进披露**：时间线首屏只显示「过去 X 天」的入口卡片，用户点进去才展开事件流，避免打开即看到全部；
4. **验收补充**：4 项验收拆成「离线 1 天」「离线 3 天」「离线 30 天」三个用例，且明确 30 天场景的首屏展示策略。

---

### P0-2 · 数据导出/导入未定义 schema → 「数据主权」承诺与验收范围错位

**问题描述**
CONTEXT.md 把「数据主权」定义为「pet 数据属于用户，可随时导出，也可指定迁移到其它服务中心（未来）」；MVP 验收 7 只写「一键导出 pet 全部数据（JSON），可导入恢复」。

但「全部数据」到底包括什么完全没定义：
- pet 基础数据（名字、状态、创建时间）？
- 记忆片段（用户命名偏好、喜欢什么）？
- 事件时间线（含结构 + 表现引用）？
- 储物罐、物品栏？
- 账号元数据（邮箱 hash、创建时间）？
- 当前使用的素材包版本 / 事件引擎版本？
- 导出时间戳、schema 版本、校验和？

**影响**
- 未来做多中心迁移时必然踩雷：不同中心 schema 不兼容，用户数据丢失；
- 用户备份后想恢复，可能因为 schema 未版本化而无法导入；
- 数据主权沦为口号，用户无法真正迁移或自证数据归属。

**建议处理方式**
1. 在需求文档中新增一节 **「数据导出规范（v1）」**，明确：
   - 导出字段清单（pet 基础、记忆、时间线、物品、账号元数据）；
   - 排除项（会话 token、验证码记录、服务端临时元数据）；
   - JSON schema 版本号字段（`schema_version: 1.0`）；
   - 完整性校验和（SHA256）；
   - 导入失败的用户友好提示（版本号不匹配、校验和失败、字段缺失各自不同的报错）；
2. **验收 7 改为**：「导出 → 清空环境 → 导入 → 数据逐字段比对一致」的自动化测试通过；
3. 多中心迁移作为 v2 需求，但 schema 与版本号从 MVP 就预留。

### P0-3 · 无密码账号体系的安全与恢复闭环未定义

**问题描述**
MVP 采用「邮箱 + 邮箱验证码」无密码登录。文档没有明确：
- 验证码有效期、复用窗口、单邮件频率上限；
- 登录后会话时长（token 有效期）；
- 用户账号被盗后如何找回（没有密码可改，只能依赖邮箱控制）；
- 邮件域被黑时（如 corporate mail / 公共邮箱被批量劫持）的账号批量失陷风险；
- 验证码是否只用于注册，还是每次登录都要重发？

**影响**
- 「数据主权」反噬：账号被劫持 = pet 的历史与记忆被劫持，用户失去数据（甚至比 SaaS 更糟，因为 SaaS 还有密码兜底）；
- 攻击者可批量劫持一个邮件域下所有账号，形成系统性风险；
- 用户长期体验下降：每次登录都要重新收验证码，与「低摩擦」定位冲突；
- 与「少打扰」冲突：邮件验证码本身就是一种强触达，频率失控会打破原则。

**建议处理方式**
1. **明确技术边界**：
   - 验证码注册后发放**一次性 magic link / 短期 token**（30 天有效），后续登录不需重新发验证码；
   - 验证码本身：有效期 10 分钟、同邮箱 5 分钟内只允许 3 次、IP 维度全局限流；
2. **补一个「账号申诉」机制**（哪怕 v2 完整做，MVP 也要留人工兜底通道）：
   - 邮箱丢失时如何找回 pet 数据；
   - 建议：账号创建时同时提供一个「数据导出备份文件 hash 记录」，申诉时可用备份比对身份；
3. **验收补充**：账号体系安全与恢复独立成一项（节流测试、token 过期、导入备份作为身份证明），当前 11 项完全没覆盖。

---

### P0-4 · 「记忆引用」这个灵魂体验，验收未覆盖

**问题描述**
CONTEXT.md 反复强调「活人感 + 有记忆」是核心体验；文档 3.2 定义 pet 有「用户叫它什么、喜欢什么、收过哪些物品」的基础记忆；3.3 说事件引擎根据「pet 状态、记忆与流逝时间」生成事件；3.7 说回信「可引用所收物品与历史记忆」。

但 11 项验收里，没有任何一项验证「pet 真的会引用历史记忆」：
- 验收 3（随机事件引擎）只测「会低频产生事件」；
- 验收 5（事件流）只测「单向输出」；
- 验收 11（回信）只测「写一封信」；
- 没有验证：pet 被命名为「小圆」后，事件文案能否自然带入「小圆」？用户送过浆果后，回信能否提及「上次你送我的浆果」？

**影响**
- 产品的核心差异化（区别于普通随机事件生成器）在验收环节无法被保证；
- 工程实现可能只做了「事件模板 + 参数替换」，没有真正的记忆检索层；
- 用户第一次玩到 30 天后发现 pet 完全不记得任何事，直接判死。

**建议处理方式**
1. 在 3.3 事件引擎中明确「记忆引用」的最低要求：
   - 用户命名：事件文案中至少 30% 概率自然引用 pet 名字；
   - 物品记忆：回信中至少 1 次提及最近 3 次馈赠物品中任意一件；
   - 时间锚点：事件引用「几天前」「上周」类时间表达；
2. 验收 11（回信）扩展为「回信必须包含至少 1 条记忆引用（可量化：含物品名 / 用户命名 / 时间锚点任一项）」；
3. 新增验收：事件文案抽样检查，验证记忆引用的正确率不低于阈值。

## 2. P1 · 中优先级问题（批量）

### P1-1 · 「无社交压力」与「每日馈赠 + 回信」节奏的隐性 KPI

- 每日登录 → 拿物品 → 送 pet → 次日/当晚收信，形成「日频仪式」闭环；
- 与「不追留存、不强制互动」在理念层有张力；
- 用户 3 天没登录期间：pet 完全无馈赠无回信（时间线空窗期），呈现方式未定义；
- **建议**：回信不必强绑定「喂食后」——pet 也可以自主回信（如「昨晚梦见你了」），降低每日打卡压力；用户引导文案严格避免「打卡」「签到」等暗示语言。

### P1-2 · 术语冲突：「单机」≠「不联网」需要更清晰的用户表达

- CONTEXT.md 已定义「单机模式」= pet 间不交互但可与外部服务通信；
- MVP 文档 3.8「pet 每次联网同步时拉取公告」——用户角度容易理解成「pet 不联网」；
- **建议**：在面向用户的说明中改用「独立生活模式」/「pet 各自过各自的」等更直白的表达，避免技术术语泄露到产品文案。

### P1-3 · 「公告」触达的最小闭环缺失

- 无「已读/未读」标记；无「静音/免打扰」入口；无历史公告回溯；
- 用户在 3 个月后才同步，收到 N 条历史公告——是否展示全部、按时间倒序、还是只显示最新？未定义；
- **建议**：公告至少支持「已读/未读」「静音 N 条」「按时间倒序列表」；空窗期回补的公告走同一 P0-1 的聚合摘要策略。

### P1-4 · pet 状态机在补算期间的同步规则缺失

- 3.2 定义状态：在家 / 出门散步 / 旅行中；
- 3.4 补算时「世界不推进」——离线 3 天期间 pet 状态如何变化？离线前「在家」→ 离线期间是否出门过 → 回来时状态是啥？
- **建议**：明确「补算期间 pet 状态机也按流逝时间推进」，且状态转换与事件引擎耦合输出（出门事件 → 触发状态切换到「出门」）。

### P1-5 · 「每日馈赠」的物品池范围与空池兜底未定义

- 首次登录从「物品池」随机取一件；物品池内容、大小、抽取规则未定义；
- 用户长期在线时物品池是否会耗尽？重复物品如何处理？
- **建议**：定义物品池最少 N 种物品、抽取规则（均匀 / 加权 / 排除最近重复）、池空时的兜底文案。

### P1-6 · 事件流的排序、分页与「记忆引用展示」未定义

- 回信也是事件类型（CONTEXT.md 明确）——时间线上是混杂在普通事件中，还是独立区块？
- 补算后 N 条事件如何分页？（见 P0-1 的摘要策略）
- 记忆引用如何在时间线上高亮？
- **建议**：明确时间线是「事件按时间轴 + 类型标签」的单一列表；记忆引用在事件卡片内以浅灰底色或角标呈现。

### P1-7 · 会话时长与「不重新发验证码」的 UX 权衡

- 相关于 P0-3，但独立成项强调 UX 层面：
- 用户每次打开 Web 都要收验证码 → 与「低摩擦」定位冲突；
- **建议**：至少 30 天免登（token 有效期）；提供「退出登录」入口。

### P1-8 · 术语「极端必要场景」的邮件推送滥用风险

- CONTEXT.md 提到「极端必要场景由运营方使用邮箱推送」——「极端必要」无边界；
- **建议**：定义邮件推送白名单（账号安全、系统故障、迁移通知、严重 bug 告知），且每次推送留审计日志。

### P1-9 · 事件引擎与素材包的插槽契约（plugin contract）未定义

- 「事件引擎不关心表现、素材包不关心逻辑」是核心原则，但插槽怎么定义？事件类型有哪些？每种事件需要什么素材？
- **建议**：在需求文档中补一节「事件-素材契约」，列出 MVP 覆盖的事件类型枚举与每个事件需要的素材/文案插槽；这也是未来插件生态的起点。

### P1-10 · 「补算」语义的三处不一致

- requirements.md 3.4：「下次启动时」——开发者可能理解为「前端页面下次打开」；
- CONTEXT.md：「下次服务启动时」——服务端进程；
- 实际 MVP 是 Web 应用，没有本地服务进程；
- **建议**：明确补算发生在**服务端**「用户下次发起同步请求时」，而非「服务进程重启时」。这是实现层面的关键区分。

## 3. P2 · 低优先级建议

1. **公告时区**：跨时区用户看到的公告时间戳如何显示？建议显示 UTC+8 或用户本地时区，二选一并在文档中固定。
2. **回信延迟策略**：「次日 / 当晚」在 MVP 中二选一即可，不必两个都实现——建议固定「喂养后 24 小时内随机生成」，实现简单也符合理念。
3. **素材包目录规范**：MVP 内部定死一套目录结构即可（`assets/icons/*.png`, `assets/text/*.json`），后续再公开规范。
4. **用户创建 pet 的 UI 引导**：账号创建即拥有第一只 pet——但用户怎么命名 pet？MVP 是否提供命名入口？建议保留最小命名 UI。
5. **宠物命名后可否改名？可否删除？**：MVP 可以先不做，但需求里明确「明确不做」以避免验收时的争论。
6. **数据导出前的用户确认弹窗**：导出前明确提示「包含哪些数据、不包含哪些」，避免用户误解。
7. **数据导入的用户友好提示**：版本号不匹配 / 校验和失败 / 字段缺失，给不同的用户友好文案。
8. **性能指标进入验收**：文档要求「页面加载 <3s」「补算秒级」，但验收未包含。建议在验收中加一条性能冒烟。
9. **验收 10 和 11 建议合并**：每日馈赠闭环 = 登录拿物品 + 送 pet + 收回信，是一项完整的用户体验，拆开测反而会漏掉中间断点；合并后可释放一个验收配额给 P0-2 / P0-3 / P0-4 缺的项。
10. **安全审计日志**：即使 MVP 不对外暴露，服务端内部至少记录验证码尝试、登录失败、导出/导入操作——方便未来做「数据主权」自证。
11. **导出文件的元信息**：导出 JSON 内带 `exported_at`, `exported_from`（服务中心标识）, `schema_version`——便于跨中心识别来源。

## 4. 遗漏场景补充（不在文档里但产品必须考虑）

- **用户长期离线后回归**：见 P0-1，聚合摘要 + 渐进披露。
- **用户账号被盗后找回**：见 P0-3，人工兜底通道。
- **邮件域被黑批量劫持**：见 P0-3，需邮件服务商侧风控配合或域名白名单。
- **pet 被命名后用户想改名 / 删除 pet**：MVP 不做但需求明确标注。
- **多设备同时登录**：token 是否可共存？并发编辑物品栏怎么处理？
- **网络中断时正在喂食 / 送礼**：请求超时后的重试策略；用户体验（"我送了"但实际失败，会不会造成 pet 无回信？）。
- **跨时区用户**：每日馈赠的"当天"以谁时区为准？公告时间戳显示。
- **pet 无物品可送时的兜底**：物品栏空了能否继续送？还是显示空态引导？
- **导出文件过大**：长期使用后导出 JSON 可能达 MB 级——前端下载策略？
- **素材包损坏 / 加载失败**：回退到默认素材包的兜底逻辑。
- **事件引擎产出的事件在文案中引用了「不存在的历史」**（例如引用了尚未生成的记忆）：记忆检索的时序一致性。
- **验证码邮件被垃圾邮件过滤**：备用登录方式（手机短信？二次邮箱？）——MVP 不做，但需求明确说明「用户需保证邮箱可收信」。

## 5. 与竞品 / 行业参考

| 竞品 | 参考点 | aetherPet 差异 |
|------|--------|----------------|
| 旅行青蛙（旅行青蛙 / 旅かえり） | 低频、有记忆、明信片机制、日常仪式 | aetherPet 开源、可插拔、数据可导出——但 MVP 的差异化叙事需要更清晰的一句话定位（"旅行青蛙的开源、数据可迁移复刻"或更抽象） |
| Mastodon / Pleroma（去中心化联邦） | 公告协议、联邦广播、节点自治 | aetherPet MVP 不做联邦，但公告协议要预留兼容（文档已提） |
| Wooldoo / 星野 / 筑梦岛 | AI 陪伴、情绪价值 | aetherPet 明确不做 AI 对话——这是差异化，也是对「佛系」的自我克制，MVP 立场清晰 |
| OpenPet / Neopets / Tibia | 开源养宠、社区生态 | aetherPet 强调"素材包可配置"作为最轻插件入口——这个思路好，但 MVP 验收（P0 相关）需要更务实 |
| Magic Link（Zapier / Notion 等） | 无密码登录的最佳实践 | 建议直接采用（P0-3） |

## 6. 建议产品方明确回应的关键问题

在开始开发前，建议产品方确认下列关键概念，避免开发中途返工：

1. **补算的执行场景**：服务端进程启动时？用户下次请求时？用户下次打开前端时？（P0-1、P1-10）
2. **「单机模式」与「联网同步」的用户可感知边界**：用户看到 UI 时，如何理解「pet 什么时候会动、什么时候不会动」？（P1-2）
3. **邮件推送的「极端必要」场景清单与频率上限**：产品方内部要有硬规则。（P1-8）
4. **事件流的时间轴排序规则**：按事件发生时间？按 pet 状态时间？回信是"事件"还是独立区块？（P1-6）
5. **多中心迁移的 MVP 边界**：MVP 只做导出/导入，还是支持指定迁移目标中心？（P0-2）
6. **事件引擎与素材包的插槽契约**：谁定义？何时定稿？（P1-9）
7. **记忆引用的检索算法**：纯模板？最近 K 条？加权随机？语义检索？（P0-4）
8. **「极端必要」邮件推送的审批机制**：谁触发、谁审批、有记录吗？

## 7. 验收项调整建议（供需求分析师参考）

当前 11 项建议调整为：

| # | 验收项 | 具体表现 | 变化说明 |
|---|--------|----------|----------|
| 1 | 注册登录（含安全边界） | 邮箱验证码注册/登录；登录后创建第一只 pet；**同邮箱验证码节流、token 有效期、退出登录** | 合并安全边界 |
| 2 | 档案页 | 可查看 pet 当前状态、记忆片段、事件历史 | 不变 |
| 3 | 随机事件引擎 | pet 会低频随机产生事件；**文案自然引用 pet 名字** | 补记忆引用 |
| 4 | 补算（含极端场景） | 离线 1 天 / 3 天 / 30 天 分别验证；**30 天场景首屏聚合摘要 + 渐进披露** | 补封顶 |
| 5 | 事件流 | 时间线展示，宠物单向输出，无回复按钮；**记忆引用高亮** | 补记忆引用 |
| 6 | 公告 | 服务端发公告 → 用户同步可见；**已读/未读、静音、按时间倒序** | 补闭环 |
| 7 | 数据导出/导入 | 一键导出 JSON（含 schema 版本、校验和）；导入恢复后**逐字段比对一致** | 补 schema |
| 8 | 素材包可配置性 | **开发者模式下**可加载另一套素材包并看到视觉/文案变化 | 改为开发者工具验证 |
| 9 | 部署 | 官方托管可访问；自托管有文档；**性能冒烟（加载 <3s、补算秒级）** | 补性能 |
| 10 | 每日馈赠闭环 | 首次登录奖励物品 → 送 pet → **次日/当晚** pet 回信（信含至少 1 条记忆引用） | 合并原 10+11 |
| 11 | **账号安全与恢复**（新增） | 验证码节流、token 过期、账号申诉入口、导入备份作为身份证明 | 新增 |

如果 11 项配额不够，建议优先合并 10+11 释放一个配额给「账号安全与恢复」。

## 8. 结语

aetherPet 的 MVP 需求文档**方向对、骨架稳、原则清晰**，是稀缺的「反 KPI 陪伴产品」定位。作为产品专家，我认可这份文档在「佛系纪律」「数据主权」「表现与逻辑解耦」上的自洽性。

**主要风险不在方向，而在细节闭环**：
- 补算的极端场景、
- 数据导出的 schema 未版本化、
- 无密码账号的安全边界、
- 记忆引用的验收缺失——

这四项修补后，MVP 可以进入开发。**建议按 P0 → P1 → P2 顺序修补需求文档，不必整体回退。**
